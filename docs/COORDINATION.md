# 项目统筹与近期执行计划

本文件定义推进方式；任务的实时负责人、状态与证据以 [Issues](https://github.com/Y-fyan/minecraft-friends/issues) 和 [路线图 #12](https://github.com/Y-fyan/minecraft-friends/issues/12) 为准，避免在多个文档中重复维护进度。玩家控制已有 [独立探针与验证](validation/0002-player-control-reproduction.md)；#2 基础工程已完成开发客户端、普通专服和最终 JAR 独立安装验收，证据见 [运行与安装验收](validation/0005-runtime-installation.md)。正式模组玩法仍需逐项实现与验收。

## 职责与决策

- **创作者 Y-fyan**：决定产品方向、许可证、需要账号或付费服务的选择，以及正式发布；需求与技术冲突时确认取舍。
- **统筹助手（本聊天）**：维护任务依赖与优先级、拆分工作、核对接口、评审证据、整理风险与下一步，在授权范围内更新仓库。普通规划调整直接记录并推进；不代替验证者宣称测试通过。
- **认领成员**：负责所认领任务的实现、测试、文档和 PR 更新；提交前说明跨模块影响与未完成项。
- **审查者**：核对验收条件和实现证据。优先由非作者审查；无法独立审查时按贡献指南记录自审情况。

未认领的任务保持无负责人，不根据仓库写权限推断工作承诺。不把助手创建的更新当作协作者本人承诺，也不冒用其账号署名。跨聊天协调在用户授权后进行；持续定时跟踪需另行安排，本文不表示已经开启后台监控。

## 任务状态

GitHub 使用单一状态标签表示当前阶段，状态变更同时维护 Issue 说明：

| 标签 | 含义 |
| --- | --- |
| `status:ready` | 前置条件足以开始下一份明确交付，可认领 |
| `status:backlog` | 已规划，尚未进入执行；可能仍有前置依赖，不等于发生故障 |
| `status:in-progress` | 有确认的负责人及正在进行的工作 |
| `status:review` | 有待审 PR 和验证证据，等待审查 |
| `status:blocked` | 已启动工作遇到明确障碍，Issue 需记录解除条件 |
| `status:tracking` | 路线图汇总，不用于代替子任务状态 |

完成任务通过关闭 Issue 表示，移除进行中的状态；不以“PR 已打开”或“编译成功”代替全部验收。优先级 `priority:P0` 表示初期关键项或发布门槛，`priority:P1` 表示可后续集成但仍保留在已承诺范围内的任务。

## 执行与反馈节奏

1. 开始一轮工作前检查任务、PR 与最新主分支，避免重复开发和覆盖他人修改。
2. 每位成员同时承担一个主要实现工作包；需要并行时先拆分文件或接口边界。
3. 认领时在 Issue 写明交付物、方案和依赖，维护者确认后立即设置 Assignee 和唯一状态标签。开始工作用 `status:in-progress`；阻塞时切为 `status:blocked` 并记录解除条件，不能同时保留两种状态；恢复后再切回。
4. 有实际进展、阻碍或接口变更时更新 Issue/PR；不要求无变化时刷状态。使用“已完成 / 验证证据 / 阻碍 / 下一步”四项即可。
5. 进入审查前按 PR 模板提供结果、测试和限制。部分 PR 使用 `Refs`，完整满足任务再 `Closes`。
6. 合并后检查依赖是否解除，更新下游任务标签及下一份交付物。每个里程碑结束时核对范围、未解决风险与进入下一阶段的证据。

新增需求先记录价值与验收，判断是否阻碍当前闭环。一般体验增强放入后续任务；改变目标版本、玩家控制路线、隐私/费用或发布范围的调整由创作者确认。
